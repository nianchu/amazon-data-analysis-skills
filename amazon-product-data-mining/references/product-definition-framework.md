# Product definition framework

Create a fresh definition for every target product.

## 1. State the unique product identity

Describe:

- Core job to be done.
- Target user and primary use scene.
- Starting input, material, signal, or problem state.
- Required output, result, or retained function.
- Indispensable mechanism, physical form, or workflow.
- The shortest functional statement that separates the product from adjacent products.

Do not define a product by search keywords, category placement, appearance, or compatibility examples alone.

## 2. Convert identity into gates

Create auditable gates:

- `G1...Gn`: conditions every core product must satisfy.
- `E1...En`: allowed extensions that retain the core identity.
- `X1...Xn`: boundaries that distinguish adjacent but different products.

Each gate must be testable from Listing evidence. Avoid subjective gates such as “looks similar.”

## 3. Test counterexamples

Before screening the full pool, test:

- Clear positive core products.
- Allowed extension products.
- Keyword-matched products with reversed direction.
- Accessories, replacements, bundles, and consumables.
- Products for the same scene that solve a different job.
- Products with the same output but a different input or mechanism.

Revise the definition until the positive rules admit legitimate extensions and reject adjacent products without enumerating ASINs one by one.

## 4. Create the product-specific parameter schema

Extract recurring variables from representative Listings:

- Identity variables.
- Performance/specification variables.
- Material or form variables.
- Compatibility variables.
- Feature variables.
- Included-component or bundle variables.
- Compliance variables where relevant.

Use controlled values and units suitable for pivot tables. Keep evidence and conflicts traceable.
